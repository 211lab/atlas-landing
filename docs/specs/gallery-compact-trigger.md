# Compact background gallery and authenticated generation request

## Goal

Simplify each gallery card to one weather/model metadata line, tuck recipe chips into a disclosure, and provide a safe authenticated route from the gallery to request a new background generation.

## User-visible behavior

- Each image card shows one metadata line in this order: `YYYY-MM-DD HH:MM · {weather}, {temperature}°F, wind {speed} mph, clouds {coverage}%, precip {amount} mm/h · model: {image model}`. Omit unavailable optional values without adding other metadata labels.
- The timestamp has no extra `local`/`UTC` suffix. Do not show standalone time labels, fixed wildstyle text, or vision-model text on image cards.
- Convert stored wind speed from km/h to mph. **ASSUMPTION:** The example's `mph/h` means standard wind speed `mph`, not miles-per-hour-per-hour.
- Place all randomized facet chips inside one collapsed `Visual recipe` disclosure per image. Do not show the full prompt or any other per-image text by default. Keep the full-size image link and lazy thumbnail behavior.
- Add a gallery-level `Generate new background` link to the authenticated Gitea Actions page for the `generate-background` workflow. The user signs in if necessary and presses Gitea's `Run workflow`; the gallery never embeds credentials or invokes the Kubernetes API.
- Running the workflow writes a unique request ID to GitOps. Argo CD creates one normal one-off Job from the same generator settings/secret/PVC as the CronJob. A later request changes the ID; automated prune removes the prior manual Job. The job is not an Argo hook, so unrelated syncs do not repeat it.
- The generator Job uses no Kubernetes API permissions; the workflow uses existing Gitea GitOps credentials and the authenticated Gitea UI as the trigger boundary.

## Non-goals

- No public unauthenticated run endpoint, browser-held token, direct Kubernetes API request from the gallery, or new cluster-admin credential.
- No arbitrary job parameters, image-model override, gallery deletion, or prompt editing UI.
- No change to scheduled generation timing, image verification/publishing, OpenRouter credentials, or gallery storage.

## Acceptance criteria

1. **Given** a new gallery card with full metadata, **when** rendered, **then** its only visible per-image text is one line with local timestamp, weather label, Fahrenheit temperature, mph wind, cloud percentage, precipitation in mm/h, and image model in the specified order; vision model and wildstyle labels are absent.
2. **Given** a legacy card with missing metadata, **when** rendered, **then** it remains safe and useful, omitting unavailable fields without exposing vision/style/time-zone labels or throwing.
3. **Given** a card with facet metadata, **when** the gallery loads, **then** all chips are inside a collapsed `Visual recipe` disclosure and no prompt details are visible by default.
4. **Given** the gallery is open, **when** the user activates `Generate new background`, **then** the browser navigates to the authenticated Gitea Actions page for the generator workflow; no token or Kubernetes API request is present in browser code.
5. **Given** an authorized Gitea user runs `generate-background`, **when** the workflow completes its GitOps request commit, **then** the workflow writes a unique run ID to the configured Atlas values file and exits successfully.
6. **Given** Argo CD reconciles a new run ID, **when** it applies the manual Job, **then** the Job uses the current generator image, OpenRouter secret, weather configuration and shared background PVC; it has bounded runtime and no K8s API permissions.
7. **Given** the run ID remains unchanged, **when** an unrelated Argo sync occurs, **then** the completed manual Job is not recreated. **When** a later workflow writes a new ID, **then** Argo prunes the previous Job and creates the new one.
8. **Given** app and GitOps chart changes, **when** tests/rendering run, **then** Python tests, Helm rendering, homepage audit, Pages/CI validation as relevant, and secret scanning pass; no imperative cluster apply is used.

## Constraints and design

- Gallery HTML is generated by `generator/generate.py` into the shared data volume; preserve escaping for all metadata and attributes.
- Store `manualGenerateRunId` as a top-level chart value. The Gitea workflow updates only this field in the GitOps values file; no runtime credentials enter gallery HTML.
- The Job is a normal Argo-managed manifest with a stable unique name based on run ID (not a Sync hook). Do not set a short TTL that would make self-heal recreate an old run while its ID remains desired.
- Keep the CronJob's live time/weather lookup and generator behavior unchanged.
- The public app source and Atlas internal source use different histories. Publish code on separately based branches; never force-update either history.

## Ordered implementation plan

1. Update generator gallery rendering and tests for the one-line caption, mph conversion, hidden style/vision labels, recipe disclosure and authenticated action link.
2. Add `.gitea/workflows/generate-background.yaml` with `workflow_dispatch`; safely write a unique `manualGenerateRunId` to the configured GitOps values path using existing repo credentials.
3. Add the one-off Job template and `manualGenerateRunId` value to the Atlas landing chart; update the runbook with the button/workflow operation and GitOps cleanup semantics.
4. Validate Python tests/compile, Docker build, Helm template rendering, GitOps repository audits, and Gitleaks. Push through GitHub and Atlas topic branches/PRs, merge after checks, and let Argo reconcile the chart.
5. Verify the generated gallery line/disclosure, Gitea workflow link, rendered Job security/resources, and Argo state. Roll back by reverting app and chart/workflow changes through GitOps.
